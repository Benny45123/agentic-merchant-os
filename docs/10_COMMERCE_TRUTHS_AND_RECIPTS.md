
# 10 — Commerce Truth & Decision Receipts Spec

## 1. Purpose

Every money-relevant decision — approved, blocked, or requiring confirmation — produces exactly one immutable `Receipt`. This is the system's "commerce truth": a human (or judge) should be able to look at one Receipt and understand exactly why a transaction did or did not happen, without reading code or logs.

## 2. Receipt Contents (see `05_DATA_MODEL.md` §Receipt for the schema)

A Receipt captures, frozen at decision time:

- `receipt_id`, `decision_id`, `intent_id` (or `campaign_proposal_id`)
- Buyer intent as submitted (`items_snapshot`)
- Catalog state used for the decision (`catalog_snapshot_ids`, plus the authoritative price/inventory actually used)
- The mandate that was checked (`mandate_snapshot`) — frozen copy, not a live FK dereference
- The policy that was checked (`policy_snapshot`) — frozen copy, includes `version`
- Every Guardian check run, in order, with pass/fail and a human-readable detail string (`guardian_checks`)
- The final decision and primary reason
- Razorpay order/payment IDs if a payment was attempted
- Failure reason if blocked

## 3. Why Denormalized

Mandates and Policies change over time (a merchant might loosen `minimum_margin_pct` next week). If a Receipt only stored `mandate_id`/`policy_id` as foreign keys, looking at an old Receipt after a policy edit would show the *current* policy, misrepresenting what was actually checked. Freezing snapshots into the Receipt itself guarantees the audit trail never lies, at the cost of some storage duplication — an acceptable and correct tradeoff for an audit system.

## 4. Replayability

`POST /receipts/{id}/replay`:

1. Load the Receipt's frozen `items_snapshot`, `mandate_snapshot`, `policy_snapshot`, and the authoritative catalog state **as it was at decision time** (from `catalog_snapshot_ids` → `CatalogSnapshot` rows, which are themselves immutable).
2. Re-run `check_mandate()`, `check_policy()`, and the price/inventory comparison logic — all pure functions per `07_GUARDIAN_SPEC.md` §7 — against this frozen data.
3. Compare the replayed decision to `Receipt.decision`. `matches_original: true/false`.
4. This is a genuine correctness proof, not a cosmetic feature: if `matches_original` is ever `false` for an un-edited receipt, that indicates a non-determinism bug in the Guardian pipeline, and `14_TEST_PLAN.md` includes a nightly/CI job that replays every stored receipt and asserts 100% match.

## 5. What a Receipt Is NOT

- Not a substitute for `Order`/`Payment` rows (those remain the Razorpay-facing source of truth for payment status).
- Not editable. No `PATCH`/`PUT` endpoint exists for Receipts. Corrections happen by creating a new decision (e.g., a refund produces its own audit entry in `Order.status`), never by mutating history.
- Not generated by an LLM. The receipt's `guardian_checks` and `reason` strings are generated by deterministic template functions from the check results, not by asking an LLM to "write a summary." (The Commerce Agent may separately paraphrase the receipt in natural language to the buyer in chat — that paraphrase is not the receipt itself and is never stored as the audit record.)

## 6. Blocked-Transaction Receipts

A `BLOCK` decision still produces a full Receipt with `razorpay_order_id: null`. This is required for the Failure Demos (`15_DEMO_SCENARIOS.md`) — the audit trail must show blocked attempts, not just successful ones. `blocked_attempt_count` on the dashboard (`04_API_CONTRACTS.md` §9) is computed by counting `Receipt.decision == 'BLOCK'` rows.

## 7. Revenue Attribution From Receipts (Rule 6 compliance)

`GET /dashboard/revenue` never contains a hardcoded number. Every field is a live aggregation:

```sql
-- total_revenue
SELECT SUM(amount) FROM "Order" WHERE status='PAID' AND merchant_id=:m AND created_at BETWEEN :from AND :to;
-- upsell_revenue: orders whose items include a SKU that was present in `recommendations[]` at cart time
--   (tracked via a `Order` -> `TransactionIntent.items` join, flagging items whose CartItem was added
--    via an accepted recommendation — see `06_AGENT_SPEC.md` §4; the Agent tags such CartItems with
--    `source: 'upsell'` so this is queryable, not inferred after the fact)
-- campaign_revenue
SELECT SUM(amount) FROM "Order" WHERE campaign_id IS NOT NULL AND status='PAID' ...;
-- blocked_attempt_count
SELECT COUNT(*) FROM "Receipt" WHERE decision='BLOCK' AND merchant_id=:m ...;
```

## 8. Receipt UI Requirement (Frontend)

The frontend must render a Receipt as a readable timeline, not raw JSON: intent → checks (pass/fail list) → decision → payment outcome. This is the artifact judges will look at during the "audit trail" portion of the demo (`15_DEMO_SCENARIOS.md`).
